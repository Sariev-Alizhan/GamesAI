## Часть 1 — Общий контекст

### Что мы делаем и зачем?

**Boilergen** — внутренний инструмент-генератор. Из одного YAML-описания создаёт код во всех слоях стека.

**Боль, которую решаем:** в Grand Games **до 3 месяцев на ивент**, и значительная часть этого времени — рутина: программист руками копирует одну и ту же структуру в C++ сервер, Node API, Flutter админку, локализацию, миграции. На каждой новой сущности — те же 4–6 одинаковых файлов с подстановками.

**Что меняем:** заменяем ручной копипаст на детерминированную генерацию. Не AI-предсказание, не "магия" — простая шаблонная подстановка. **Гарантированно 100% повторяемо**, ноль регрессий.

### Это AI-инструмент?

**Сам Boilergen — НЕТ.** Это классический code generator (как Plop/Hygen, но кастомный под GM1). Детерминированный, без LLM, без сети.

**Параллельно** идёт стратегический трек "AI в Grand Games" — Cursor/Claude Code для команды, AI-ревью бот, AI-генерация YAML из русского описания. Это **отдельные инициативы**, не часть Boilergen MVP. См. `ROADMAP.md`.

### Что ты от меня ожидаешь?

Три конкретные вещи (повторяю из брифа):

1. **30 минут встречи** — пройтись по вопросам ниже (блоки 02–04 особенно).
2. **Доступ к репо GM1 на чтение** — мне нужно посмотреть как у вас структурирован код, чтобы написать правильные шаблоны.
3. **Один пример сущности** — последняя добавленная в GM1 (например, профессия) — все файлы которые трогали, в одном документе. Это **референс** для шаблонов.

После этого я за 1.5–2 недели делаю реальные шаблоны, и мы тестируем на одной живой сущности.

## Часть 2 — Архитектура: GM1 и GM2

### TL;DR

**Одна и та же игра, два технологических стека:**

| | **GM1** (продакшен) | **GM2** (в разработке) |
|---|---|---|
| Игровой движок | свой C++ | Unity (C#) |
| Бэкенд | Node.js + Flutter админка | Node.js |
| Контент сущностей | концептуально те же типы (профессии, оружие, машины, бизнесы) | те же типы концептуально |
| Код | весь свой, на C++ | весь свой, на C#/Unity |
| Пересечение кода | **ноль** | **ноль** |

**Boilergen MVP — только под GM1.** GM2 — отдельный плагин в будущем (или общий schema-слой, см. ниже).

### Почему сначала GM1?

1. GM1 в продакшене → инструмент сразу даёт измеримую экономию
2. У меня сейчас доступ только к GM1-команде (тебе)
3. GM2 ещё в разработке — там команда сама строит каркас, не успевает на интеграции

### Как поддерживается GM2 (когда дойдёт)?

Архитектура Boilergen построена под это. **Структура плагинов:**

```
plugins/
├── gm1/                            ← наш текущий плагин
│   └── targets/
│       ├── cpp-server/
│       ├── node-api/
│       ├── flutter-admin/
│       └── shared/                 (i18n, миграции БД)
│
└── gm2/                            ← добавится позже
    └── targets/
        ├── unity-client/
        ├── node-api/
        └── shared/
```

**Два плагина изолированы.** Ноль кода переиспользуется. Это правильно, потому что:
- C++ сервер GM1 ≠ Unity клиент GM2 (даже похожие классы пишутся принципиально по-разному)
- Node API GM1 ≠ Node API GM2 (могут быть разные базы, ORM, фреймворки)

### Может ли быть **общая часть**?

Да, **возможно** — но не обязательно. Опции:

**Опция A — полная изоляция** (по умолчанию).
- Описание профессии "Бариста" в GM1 — `schemas/gm1/barista.yaml`
- Описание профессии "Бариста" в GM2 — `schemas/gm2/barista.yaml`
- Это два отдельных YAML, могут отличаться полями, могут быть синхронизированы вручную
- **Плюс:** независимость. Минус: чуть больше работы поддерживать "ту же" профессию в двух местах.

**Опция B — shared-слой** (продвинутый сценарий, если потребуется).
- Один YAML `schemas/shared/barista.yaml` описывает базовые поля (название, иконка, базовые параметры).
- Из него генерится код для **обоих** плагинов.
- Плюс: один источник правды. Минус: нужно решить какие поля общие, какие специфичные. Не нужно сейчас.

**Решение по этому вопросу — отложено** до того момента, когда GM2 встанет на ноги. Сейчас фокус только на GM1, и архитектура к **обеим** опциям готова.

### Что НЕ нужно делать сейчас

- ❌ Думать про синхронизацию контента между GM1 и GM2
- ❌ Делать общие схемы или общие шаблоны
- ❌ Привязывать решения по GM1 к будущему GM2

GM2-команда сейчас стоит на каркасе — пускай разбираются со своими движками, а мы делаем то, что **уже** даёт ROI на GM1.

## Часть 4 — Технические FAQ

### Что Boilergen умеет/не умеет

**Умеет:**
- Генерировать **новые** файлы из YAML с шаблонной подстановкой
- Inject-мод: вставлять строку в **существующий** файл (например, регистрация в роутере) — идемпотентно, через якоря
- Фильтрация шаблонов по типу сущности — оружие не лезет в файлы профессий
- Кастомные пути для каждого target в `boilergen.config.yaml`
- Dry-run превью
- Web UI для отладки

**Не умеет (и не должен):**
- Писать игровую логику
- Балансировать сущности
- Модифицировать существующие файлы произвольно (только inject в известные якоря)
- Генерировать тесты (пока)

### Безопасность

Прошёл аудит на:
- ✅ Path traversal (если кто-то напишет `id: ../../etc/passwd` — заблокировано)
- ✅ ReDoS через regex (skipIf использует substring, не regex)
- ✅ Прототайп-пollution через YAML
- ✅ Strict-mode схемы (опечатки в полях ловятся)
- ✅ HTML-escape **отключён** (мы генерим код, не HTML — это специально)
- ⏳ Аудит реальных шаблонов GM1 — после Этапа 3

**183 теста**, прогон ~1 сек, защищён от очевидных эксплоитов.

### Производительность

- Генерация одной сущности с 4–6 файлами: **<100ms**
- Парсинг YAML 1MB: <100ms
- Большой плагин (30 шаблонов): загружается за <50ms

### Зависимости

| Пакет | Зачем |
|---|---|
| `handlebars` | Шаблонный движок |
| `zod` | Валидация YAML-схем |
| `commander` | CLI |
| `chalk` | Цветной вывод |
| `js-yaml` | Парсер YAML |
| `express` | Веб-плейграунд |

Стандартные, не экзотика. Всё знакомо команде.

### Как добавить новый тип сущности?

1. Создать папку `plugins/gm1/targets/<target>/<entity-type>/`
2. Положить туда `.hbs` шаблон
3. Описать сущность в `schemas/gm1/<id>.yaml` с `type: <entity-type>`
4. Запустить `boilergen generate <yaml>` — готово

Без правок ядра. Без перекомпиляции. Без коммитов в core/.

### Как добавить новый target (например, миграция БД)?

1. Создать папку `plugins/gm1/targets/db-migration/<entity-type>/`
2. Положить шаблон с расширением `.sql.hbs`
3. В `boilergen.config.yaml` проекта прописать куда класть `db-migration`
4. Готово

### Как написать inject-шаблон?

Пример: автоматически зарегистрировать новый контроллер в роутере GM1.

```hbs
---
to: src/router.ts
inject: after
anchor: "// REGISTER_CONTROLLERS"
skipIf: "{{camelCase id}}Controller"
---
import { {{camelCase id}}Controller } from './controllers/{{kebabCase id}}.js';
router.use({{camelCase id}}Controller);
```

Что произойдёт при `boilergen generate barista.yaml`:
1. Откроет `src/router.ts`
2. Найдёт строку `// REGISTER_CONTROLLERS`
3. Если в файле уже есть `baristaController` (skipIf) — пропустит (идемпотентно)
4. Иначе вставит две строки после якоря
