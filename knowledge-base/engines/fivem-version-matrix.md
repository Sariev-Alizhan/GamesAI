# FiveM / Cfx.re version matrix

> Reference for version-aware FiveM resource codegen. Used by AI Describe RAG
> when generating fxmanifest.lua + client/server/shared scripts. FiveM's
> versioning is **less linear than Unity** — the engine itself updates
> continuously, but `fxmanifest.lua` declares a **manifest version** (`fx_version`)
> that pins certain script behaviours, AND the **framework forks** (qbcore /
> Qbox / ESX) each have their own semver lifecycle layered on top.
>
> **Versions covered:** fx_version `cerulean` / `adamant` / `bodacious` (current).
> Lua 5.3 / 5.4. qbcore / qbx_core / overextended/ox_core. **Last verified:** 2026-05-03.

## Three independent versioning axes

FiveM resources have **three** version dimensions, all of which must be coherent:

1. **Cfx.re engine / artifact build** — continuously updated server/client binaries. Server admins pin via `start_server_artifact`. Latest stable in 2026 is the **bodacious** generation.
2. **`fx_version` manifest version** — declared at the top of every `fxmanifest.lua`. Tells the engine which set of script behaviours to apply.
3. **Framework version** — qbcore (e.g. v1.3.0), Qbox/qbx_core (e.g. v1.23.0), ESX, or no framework. Resources written for qbcore v1.2 may not work on qbox without minor rewrites.

A resource generated by Boilergen pins all three: `fx_version 'cerulean'` (manifest), `dependencies { 'qb-core' }` with implicit assumption of v1.3+, runs on Cfx.re bodacious or newer artifact.

## fx_version generations

These names are FiveM's manifest-format codenames. Each generation enables a slightly different subset of script behaviours and engine features. Newer generations are backwards-compatible — older generation manifests still work.

| Generation | Year released | What it gates | When to use |
|---|---|---|---|
| `adamant` | 2018 | Original modern manifest format. Replaces legacy `__resource.lua`. | Don't pick this for new resources |
| `cerulean` | 2019 | Adds resource metadata, scripts loading order, `dependencies` block, `lua54 'yes'` opt-in | **Default for new resources** — used by every Boilergen-generated manifest |
| `bodacious` | 2024 | Adds finer-grained loader controls, additional metadata fields | Only if you need bodacious-only features; otherwise stick with `cerulean` |

`cerulean` covers everything Boilergen's `fivem-qb` target needs. `bodacious` adds capabilities most studios don't use. Avoid the temptation to declare the latest generation just to be modern — pick the lowest one that supports what you actually use.

## Lua runtime versions

| Runtime | Manifest declaration | Status |
|---|---|---|
| Lua 5.3 | (default if `lua54` omitted) | Legacy. Still supported for backwards compatibility. |
| **Lua 5.4** | `lua54 'yes'` in fxmanifest | **Recommended for new resources.** Adds integer division `//`, bitwise operators, `<close>` annotations, generational GC. Required by qb-core v1.3+, qbx_core, ox_lib, ox_inventory. |

Boilergen's `fivem-qb` target always emits `lua54 'yes'`. Modern QBCore framework requires it (qb-core's own fxmanifest declares it), so consumer resources must too — or they crash on first encounter of a 5.4 idiom in qb-core.

## Framework version landscape

### qb-core (canonical QBCore)

- Repo: [qbcore-framework/qb-core](https://github.com/qbcore-framework/qb-core), GPL-3
- Versions: v1.0 → v1.3.x current (2026)
- v1.2.6 was a long-stable release; v1.3.0+ adds player metadata system, improved oxmysql integration
- **Boilergen's `fivem-qb` target assumes qb-core v1.3+**

### qbx_core (Qbox — modern fork)

- Repo: [Qbox-project/qbx_core](https://github.com/Qbox-project/qbx_core), see LICENSE
- Versions: v1.0 → v1.23.0 current (April 2025)
- Modern rewrite of QBCore concepts. Built on `ox_lib` from the start. Cleaner code, `qbx:` namespaced events, ox_inventory native.
- **API-compatible with qb-core in most places.** Boilergen-generated resources work on Qbox without changes for the `Config` + `exports['qb-core']` patterns.

### overextended/ox_core (Ox stack)

- Repo: [overextended/ox_core](https://github.com/overextended/ox_core), LGPL-3
- Versions: v1.0 → v1.5.10 current (April 2026)
- Different design philosophy: server-authoritative entities, statebag-driven sync, TypeScript + Lua. NOT API-compatible with qb-core — resources designed for ox_core are different shape.
- Boilergen does NOT currently target ox_core. **Future plugin candidate** (`fivem-ox` sibling to `fivem-qb`).

### ESX (legacy alternative)

- Repo: esx-framework/esx_core
- Status: still actively maintained but losing market share to qbcore/Qbox
- Different shape than qbcore — uses xPlayer, MySQL.Async (legacy) instead of oxmysql, ESX events
- Boilergen does NOT currently target ESX. Track as future plugin if a real ESX studio shows interest

## Breaking changes table (within FiveM ecosystem)

| Area | Before | After | Workaround |
|---|---|---|---|
| Manifest format | `__resource.lua` (pre-2018) | `fxmanifest.lua` (`fx_version 'cerulean'`+) | Drop `__resource.lua`, write `fxmanifest.lua`. Engine still reads legacy but emits warnings. |
| Lua version | Lua 5.3 default | Add `lua54 'yes'` | Required for qb-core v1.3+ compat. Add the directive; existing 5.3-only code still runs. |
| QBCore access | `@qb-core/import.lua` shared_script | `exports['qb-core']:GetCoreObject()` runtime | Modern: drop the shared_script, declare `dependencies { 'qb-core' }` only, access at runtime. Boilergen's templates use the modern pattern. |
| MySQL access | `mysql-async` (legacy) | `oxmysql` | Replace `MySQL.Async.execute(...)` with `MySQL.update(...)` (oxmysql wrapper API). Pin `dependencies { 'oxmysql' }`. |
| Job grade keys | numeric `[0]`, `[1]` | string-int `['0']`, `['1']` (post-v1.2) | qb-core changed mid-v1.2 to string keys. Match qb-core version. |
| Inventory access | `qb-inventory` | `ox_inventory` (Qbox default), `qb-inventory` legacy | Resources should be agnostic; use `exports[Inventory]:AddItem(source, item, count)` where Inventory is config-set per server. |

## fxmanifest version matrix

Rows = manifest features. Columns = generations.

| Feature | adamant (2018) | cerulean (2019, default) | bodacious (2024) |
|---|---|---|---|
| `fx_version 'X'` declaration | required | required | required |
| `game 'gta5'` / `games {'gta5'}` | required | required | required |
| `dependencies { ... }` block | supported | supported | supported |
| `lua54 'yes'` | supported | supported | supported |
| `client_scripts` / `server_scripts` / `shared_scripts` | supported | supported | supported |
| `files { 'pattern/*.png' }` glob | supported | supported | supported |
| `provide 'other-resource-name'` (replacement claim) | not avail | supported | supported |
| `node_version '22'` (Node.js script runtime) | not avail | supported | supported |
| Fine-grained loader phases | not avail | not avail | supported |
| Resource metadata custom fields | basic | enhanced | full |

**For Boilergen-generated manifests**, `cerulean` covers everything we need. Don't bump to `bodacious` unless a specific feature is required.

## Mobile / multi-platform notes

FiveM is **PC-only** (Windows / Linux for client; Linux for server). RedM (Red Dead Online modding) shares the engine but targets RDR2.

- No iOS, no Android, no console builds
- Server-side runs on Linux (`alpine` or `ubuntu` base for Docker images is common)
- Linux file systems are **case-sensitive** (the source of `dependency-case-mismatch` failures Boilergen's Schema Validator catches — see [`engines/fivem-cross-resource-patterns.md`](./fivem-cross-resource-patterns.md))

For studios shipping cross-platform RP (e.g. Grand Mobile on Android using a custom client), FiveM's PC-only constraint means **GamesAI's `fivem-qb` plugin is for FiveM-server studios specifically**, not for cross-platform mobile RP. Different wedge.

## Backwards-compat recipes for codegen

### Modern `fxmanifest.lua` template (Boilergen's default)

```lua
fx_version 'cerulean'
game 'gta5'

shared_scripts { 'config.lua' }
server_scripts { 'server/main.lua' }
client_scripts { 'client/main.lua' }

dependencies { 'qb-core' }

lua54 'yes'
```

Works on every artifact build from `cerulean` onwards (2019+). Compatible with qb-core v1.3+, Qbox, and any framework that accepts `dependencies { 'qb-core' }`-declaring consumers.

### Conditional Lua 5.4 features

Lua 5.4 features (integer division `//`, `<close>` annotations) **don't have preprocessor directives** — Lua doesn't have conditional compilation. Either:

1. Declare `lua54 'yes'` and use 5.4 freely (recommended for new code)
2. Stick to 5.3-compatible syntax (use `math.floor(a / b)` instead of `a // b`)

Boilergen-generated code uses 5.3-compatible syntax even when emitting `lua54 'yes'` manifests, for maximum portability.

### qb-core version detection

If a script needs to run on multiple qb-core versions, do a runtime check:

```lua
local QBCore = exports['qb-core']:GetCoreObject()
if QBCore.Functions.AddJob then
    -- v1.0+ API
    QBCore.Functions.AddJob(name, jobData)
else
    -- legacy fallback (rare; v1.0 has shipped since 2021)
    QBCore.Shared.Jobs[name] = jobData
end
```

Boilergen's `fivem-qb` target uses `QBCore.Functions.AddJob(...)` only — assumes v1.0+.

## How AI Describe consumes this matrix

When the user asks "generate a FiveM job resource for QBCore v1.3," AI Describe:

1. Loads this entry via RAG (semantic search on "FiveM" + "QBCore" + "v1.3")
2. Pulls the **fxmanifest matrix** + **breaking-changes table** + **qb-core convention** sections
3. Emits `fx_version 'cerulean'`, `lua54 'yes'`, `dependencies { 'qb-core' }`, `QBCore.Functions.AddJob(...)` — all aligned with v1.3+

If the user later says "I'm on Qbox / qbx_core instead," AI consults the framework table, identifies that **qbx_core is API-compatible with qb-core for jobs**, and notes that the same generated code works without changes — but recommends Qbox conventions like `qbx:` namespaced events for any new event handlers added.

## What this matrix does NOT cover

- **Asset Store / community resources** (Jaksam Jobs Creator, advanced framework wrappers, etc.) — those have their own version lifecycle.
- **txAdmin** versioning — that's the server admin panel, not engine.
- **Engine internals** — the C++ Cfx.re engine itself has no public API for resource scripts beyond the documented surface.
