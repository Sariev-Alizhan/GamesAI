## Часть 1 — Общий контекст

### Что мы делаем и зачем?

**Boilergen** — инструмент-генератор. Из одного YAML-описания создаёт код во всех слоях стека (C++ сервер, Node API, Flutter админка, локализация).

**Боль:** в Grand Games **до 3 месяцев на ивент**, и значительная часть — рутинный копипаст одних и тех же структур в 4–6 файлов на каждой новой сущности.

**Что меняем:** заменяем ручной копипаст на детерминированную генерацию. Не AI-предсказание — простая шаблонная подстановка. **100% повторяемо**, ноль регрессий.

### Это AI-инструмент?

**Сам Boilergen — НЕТ.** Это классический code generator (как Plop/Hygen, но кастомный). Детерминированный, без LLM на критическом пути.

**Сверху** есть **AI Describe** — фича где ты пишешь "новая профессия таксиста" на любом языке, AI генерит YAML, дальше обычный pipeline. Опционально, не обязательно.

Параллельно — стратегический трек "AI в Grand Games": Cursor для команды, AI-ревью бот, и т.д. Это **отдельные инициативы**, см. `ROADMAP.md`.

## Часть 2 — GM1 vs GM2

### TL;DR

**Одна и та же игра, два технологических стека:**

| | **GM1** (продакшен) | **GM2** (в разработке) |
|---|---|---|
| Игровой движок | свой C++ | Unity (C#) |
| Бэкенд | Node.js + Flutter админка | Node.js |
| Контент | концептуально те же типы | те же типы концептуально |
| Код | весь свой, на C++ | весь свой, на C#/Unity |
| Пересечение кода | **ноль** | **ноль** |

**Boilergen MVP — для GM1.** GM2 — отдельный плагин потом (или общий schema-слой, см. ниже).

### Почему сначала GM1?

1. GM1 в продакшене → инструмент даст измеримую экономию
2. У меня сейчас доступ только к GM1-команде (тебе)
3. GM2 ещё в разработке — там команда строит каркас, не до интеграций

### GM2 (когда дойдёт)

Архитектура Boilergen построена под это:

```
plugins/
├── generic-rp/                     ← универсальный референс (готов)
├── gm1/                            ← специфика GM1 (ждёт твои ответы)
└── gm2/                            ← добавится позже под Unity stack
    └── targets/
        ├── unity-client/
        ├── node-api/
        └── shared/
```

Два плагина изолированы — ноль кода переиспользуется. C++ ≠ Unity. Это правильно.

### Опционально — общий shared-слой

В будущем можно сделать `schemas/shared/barista.yaml` который генерит код для **обоих** плагинов (плюс — один источник правды; минус — нужно решить какие поля общие). Не нужно сейчас.

## Часть 4 — Технические FAQ

### Что Boilergen умеет/не умеет

**Умеет:**
- Генерировать новые файлы из YAML с шаблонной подстановкой
- Inject-мод: вставлять строку в существующий файл (например, регистрация в роутере) — идемпотентно
- Фильтрация шаблонов по типу сущности — оружие не лезет в файлы профессий
- Кастомные пути для каждого target в `boilergen.config.yaml`
- Dry-run превью
- Web UI, CLI, MCP server, VS Code extension — четыре способа использовать
- AI Describe (опционально) — естественный язык → YAML через Claude

**Не умеет (и не должен):**
- Писать игровую логику
- Балансировать сущности
- Генерировать тесты (пока)
- Модифицировать файлы произвольно (только inject в известные якоря)

### Безопасность

Прошёл аудит на:
- ✅ Path traversal (если кто-то напишет `id: ../../etc/passwd` — заблокировано)
- ✅ ReDoS через regex (skipIf использует substring, не regex)
- ✅ Strict-mode схемы (опечатки в полях ловятся)
- ✅ HTML-escape отключён (мы генерим код, не HTML — это специально)
- ⏳ Аудит реальных шаблонов GM1 — после Этапа 3

**183 теста**, прогон ~1 сек.

### Зависимости

`handlebars`, `zod`, `commander`, `chalk`, `js-yaml`, `express`, `@anthropic-ai/sdk` (только AI Describe), `@modelcontextprotocol/sdk` (только MCP server). Стандартные, не экзотика.
