# ✦ Бриф для Игоря — v2

**Генератор кода для Grand v1** (с возможным расширением на v2 в будущем)

Одна YAML-схема игровой сущности — и автоматически создаётся код во всех слоях стека Grand v1. Цель: снять рутину с команды и ускорить добавление контента.

| Что прошу | Чтение | До MVP | Мой ресурс |
|---|---|---|---|
| 30 мин встречи | ≈ 4 минуты | ~1 неделя (скелет уже работает) | 4–6 ч / день |

---

## § 01  Идея

Внутренний инструмент-генератор. Описываешь игровую сущность (профессию, оружие, машину, бизнес) **один раз** в YAML — и получаешь готовый бойлерплейт во всех нужных местах кода Grand v1.

> «Профессия "бариста" описана в одном файле. При добавлении новой профессии — не открываешь 5 разных мест в репо, не копипастишь 80% похожего кода. Команда не тонет в рутине.»

**Что делает:**
- C++ серверный код (классы сущностей)
- Node API (контроллеры, роуты)
- Flutter админка (формы редактирования)
- Локализация (заглушки на все языки)
- Миграции БД (если применимо)

**Что не делает:** не пишет игровую логику, не балансирует, не заменяет геймдизайнера. Только бойлерплейт.

### Про Grand v2

v2 — отдельная игра на Unity + Node, концептуально похожая на v1, но с полностью своим кодом. **MVP делаем только под v1.** Когда v2 встанет на ноги — обсудим, имеет ли смысл вынести описания сущностей в shared YAML-слой, чтобы одна "бариста" описывалась раз и генерилась под оба стека. Это **возможная будущая фича**, не блокер сейчас.

Это не платформа и не сторонний продукт. Внутренний инструмент под наши боли. Если через 3–4 месяца увидим, что хорошо работает — обсудим расширение.

## § 02  Что уже сделано

**Скелет инструмента готов и работает на dummy-данных.** Лежит на GitHub.

- TypeScript + Handlebars + Zod, ~300 строк кода
- Парсер YAML, движок шаблонов, plugin-loader, генератор
- CLI: `boilergen generate <schema>`, `list`, `init`, `--dry-run`, конфиг-файл для проектов-целей
- Демо: 2 dummy-сущности (профессия, оружие), 6 шаблонов, 4 слоя стека (C++, Node, Flutter, JSON i18n)
- Фильтрация шаблонов по типу сущности (профессия не лезет в шаблоны оружия и наоборот)

**Могу показать вживую за 5 минут** — команда в терминале, на глазах появляются файлы. Это снижает риск, что мы тратим время на встречу "впустую": инструмент не теоретический, он уже реален.

## § 03  Архитектура

```
boilergen/
├── src/core/                    # ядро, без специфики Grand Games
│   ├── schema-loader.ts         # парсер YAML
│   ├── template-engine.ts       # Handlebars + helpers
│   ├── plugin-loader.ts         # обход шаблонов
│   ├── generator.ts             # оркестратор
│   └── config-loader.ts         # читать конфиг проекта
│
├── plugins/grandgames-v1/       # специфика v1
│   ├── config.yaml              # пути в репо v1
│   └── targets/
│       ├── cpp-server/<entity>/ # шаблоны C++
│       ├── node-api/<entity>/   # шаблоны Node API
│       ├── flutter-admin/<entity>/ # шаблоны Flutter
│       └── shared/<entity>/     # локализация, миграции
│
└── schemas/grandgames-v1/
    └── profession.example.yaml  # одна схема на сущность
```

Соглашение: `targets/<target>/<entity-type>/<file>.hbs`, где `<entity-type>` = `schema.type` в YAML. Это даёт фильтрацию: при `generate weapon ...` создаются **только** weapon-шаблоны, без каши с другими типами.

### Запуск

```bash
$ boilergen generate ./schemas/grandgames-v1/barista.yaml
  → генерация во все слои v1

$ boilergen generate ./schemas/grandgames-v1/barista.yaml --dry-run
  → preview без записи на диск

$ boilergen list
  → список плагинов и шаблонов
```

**Стек:** Node.js + TypeScript + Handlebars + Zod. Уже знаком команде. Никакой экзотики.

## § 04  Вопросы

Без ответов не могу спроектировать схемы и шаблоны под реалии Grand v1. Самые важные — **БЛОК 03**: от выбора сущности зависит, на что я потрачу следующие 1–2 недели.

### БЛОК 01 — Бэкенд и БД (IMPORTANT)

1. БД у v1 — какая (Postgres, MongoDB, MySQL)?
2. Как сейчас работают миграции БД — вручную, через ORM (Prisma, TypeORM, Sequelize), отдельный инструмент?
3. Структура Node API — Express, Nest, своё? Что использует команда?

### БЛОК 02 — Источник правды для данных (IMPORTANT)

1. Где сейчас живёт описание игровых сущностей в v1: БД, JSON-конфиги, C++ хедеры, Google Sheets, Excel?
2. Где сейчас самая большая боль с рассинхроном между источниками?
3. Есть ли уже какая-то схема данных (Protobuf, JSON Schema, GraphQL), из которой что-то генерируется?

### БЛОК 03 — Выбор первой сущности для MVP (CRITICAL)

1. Какая игровая сущность добавляется в v1 чаще всего?
2. На какую сущность уходит больше всего времени и нервов команды при добавлении?
3. Если бы автоматизация работала только на одну сущность — какую ты бы выбрал? **Это и будет MVP.**
4. Можешь дать пример последней добавленной сущности этого типа в v1 — все файлы и куски кода в одном документе? Это будет референс для шаблонов.

### БЛОК 04 — Стек v1 — детали (STANDARD)

1. Структура C++ части — игровой сервер, движок, или и то, и то? Система сборки (CMake, premake, своё)?
2. Как C++ сервер общается с Node.js — REST, gRPC, своё RPC поверх сокетов?
3. Flutter — клиент игры, админка, или и то, и то? State management (Riverpod, Bloc, Provider)?
4. Связь Flutter-админки с бэкендом — REST, GraphQL, gRPC?

### БЛОК 05 — Локализация (STANDARD)

1. Где живут ключи локализации в v1 (JSON-файлы, отдельный сервис, Crowdin/Lokalise)?
2. Какие языки поддерживаем? Полный список нужен заранее, чтобы шаблон знал, какие заглушки создавать.

### БЛОК 06 — Доступ и процесс (IMPORTANT)

1. Могу ли я получить доступ к репозиториям v1 для эксперимента (хотя бы на чтение)? К каким именно репо?
2. Процесс PR: ревью обязательно, какие правила (тесты, линтер, CI)? Хочу с первой недели вливаться в реальный процесс.
3. Code style — есть ли гайды для C++, TypeScript, Dart, или смотреть существующий код как референс?

### БЛОК 07 — Поддержка проекта (IMPORTANT)

1. Готов ли ты ревьюить мои шаблоны и давать фидбек по стилю кода — раз в 1–2 недели по 30–60 минут?
2. Кого из команды посоветуешь как первого пользователя инструмента — человек, который чаще всего страдает от рутины и готов протестировать MVP на реальной задаче?
3. Готов ли ты поддержать инициативу на встрече с директором по разработке через ~2–3 недели?

### БЛОК 08 — Открытые вопросы (OPTIONAL)

1. Видишь ли ты технические или организационные риски, которые я не учёл?
2. Если архитектура, которую я предлагаю, не подходит под наши реалии — где ты бы её поменял?
3. Думаешь ли о v2 уже сейчас — или пока полностью в v1?

## § 05  Поэтапный план

3 этапа до рабочего MVP в реальном репо.

### ЭТАП 01 — Подготовка (3–5 дней, без кода)
- [x] Cкелет инструмента (уже сделано)
- [ ] Эта встреча с тобой — ответы по блокам
- [ ] Замер baseline: засеку время добавления сущности (сяду рядом с тем, кто это делает)
- [ ] Получение референса (пример реальной сущности в коде v1)
- [ ] Доступ к репо

**Результат:** ясность по сущности, таргетам, baseline для измерения экономии.

### ЭТАП 02 — Реальные шаблоны (7–10 дней, основная работа)
- Финальная YAML-схема для выбранной сущности
- Шаблон №1: Node API (простой, не требует движка для проверки)
- Шаблон №2: Локализация (дешёвый, но эффектный для демо)
- Шаблон №3: C++ сервер или Flutter — что важнее показать
- End-to-end прогон на реальной сущности
- (Опционально, если нужно) шаблон №4: миграция БД

**Результат:** генерированный код компилируется и работает в реальном репо v1.

### ЭТАП 03 — Демо директору (3–4 дня)
- Замер «после» (сколько занимает с инструментом)
- Слайды: Боль → Магия (live-демо) → Цифры → План
- Прогон с тобой
- Презентация директору

**Результат:** зелёный свет на расширение и продолжение.
